# Практическая работа 4. Подключение REST API

Приложение «Фотостудия FocusFrame» переведено с хранилища в памяти на
настоящий сервер. Ни один экран не пришёлось переписывать: поменялась
только реализация репозиториев.

## 1. Как запустить

### 1.1. Сервер

```bash
cd server
node mock-server.js --port 8080 --origin http://localhost:5555
```

Зависимостей нет, нужен только Node.js 18 или новее.

Проверка, что сервер отвечает:

```
http://localhost:8080/api/__health
```

### 1.2. Клиент

```bash
flutter pub get
flutter run -d chrome --web-port=5555
```

Порт обязателен: `--origin http://localhost:5555` на сервере разрешает
только этот источник. Без фиксированного порта источник меняется от
запуска к запуску, и сервер начнёт отклонять запросы.

### 1.3. Другой адрес сервера

Адрес задаётся параметром сборки, а не константой в коде:

```bash
flutter run -d chrome --web-port=5555 \
  --dart-define=API_BASE_URL=http://192.168.1.10:8080/api
```

Значение по умолчанию — `http://localhost:8080/api`.

Токен доступа можно задать параметром сборки (удобно на занятии,
когда вход ещё не реализован):

```bash
flutter run -d chrome --web-port=5555 \
  --dart-define=API_TOKEN=<токен>
```

### 1.4. Учётные записи

| Логин        | Пароль          | Роль         | Что может                              |
|--------------|-----------------|--------------|----------------------------------------|
| `manager`    | `manager123`    | `manager`    | Создавать, изменять и удалять записи    |
| `admin`      | `admin123`      | `admin`      | Всё, включая физическое удаление        |

## 1.5. Роли и права

Сервер различает четыре роли. Права растут с уровнем роли, поэтому
роль `admin` может всё, что может `manager`, а `manager` — всё, что
может `client`.

| Роль | Уровень | Что может |
|------|---------|-----------|
| `client` | 1 | Только чтение каталога. Видит только свои бронирования. Изменение данных запрещено: сервер отвечает 403 |
| `photographer` | 2 | Всё, что может клиент |
| `manager` | 3 | Создание, изменение, логическое и множественное удаление записей |
| `admin` | 4 | Всё, что может менеджер, плюс физическое удаление и восстановление записей, управление пользователями |

### Гость и клиент — не одно и то же

У гостя роль тоже `client`, но он не выполнял вход. Различие нужно,
чтобы правильно объяснять ограничение: гостю предлагается войти,
а вошедшему клиенту — обратиться к менеджеру. Признак хранится в
`Permissions.isGuest`, а не выводится из названия роли.

Профиль пользователя не хранится в `localStorage`: он восстанавливается
с сервера по сохранённому токену при запуске (`SessionStore.restoreUser`).
Без этого после перезагрузки страницы приложение потеряло бы роль и
работало как гость. Протухший токен завершает сессию; недоступный
сервер — нет, чтобы при следующем запуске профиль восстановился.

### Как роли видны в интерфейсе

Правила проверки прав собраны в одном месте — `lib/core/permissions.dart`.
Экраны не сравнивают строки с названием роли, а спрашивают объект прав:

```dart
final permissions = context.watch<SessionStore>().permissions;

if (permissions.canCreate) ...   // кнопка «Создать»
if (permissions.canUpdate) ...   // кнопка «Редактировать»
if (permissions.canSoftDelete) ...  // кнопка «Удалить»
if (permissions.canHardDelete) ...  // кнопка «Стереть навсегда»
if (permissions.canRestore) ...    // кнопка «Восстановить»
```

Что делает клиент:

- **скрывает** недоступные кнопки (`lib/widgets/record_actions.dart`);
- **не пускает** в формы по прямой ссылке: маршруты форм защищены
  `_GuardedForm` в `lib/core/router.dart`, при недостатке прав
  показывается экран `NoAccessScreen`;
- **объясняет** ограничение плашкой `ReadOnlyNotice` и списком прав
  на главной странице.

Важно: всё это — удобство интерфейса, а не защита. Правило из
приложения А: клиентская проверка прав — это удобство, а защита всегда
на сервере. Обойти проверку на клиенте нельзя: сервер всё равно
вернёт 403, а содержимое `localStorage` пользователь видит в DevTools.

## 4. Преобразование сетевых ошибок в исключения предметной области

Виджеты и состояние не знают о существовании Dio. Между сетевым слоем и
остальным приложением стоит набор собственных исключений.

### 4.1. Схема

```
DioException
     │
     │  mapDioError()  /  mapHttpError()
     ▼
ApiException (sealed)
     ├── NetworkException      нет соединения, таймаут, CORS
     ├── UnauthorizedException 401
     ├── ForbiddenException    403
     ├── NotFoundException     404
     ├── ConflictException     409
     ├── ValidationException   422 + карта ошибок по полям
     ├── CancelledException   запрос отменён
     └── ServerException       5xx
```

### 4.2. Таблица соответствия

| Код | Тип | Текст пользователю |
|-----|-----|--------------------|
| 401 | `UnauthorizedException` | «Требуется вход в систему.» |
| 403 | `ForbiddenException` | «Недостаточно прав для этого действия.» |
| 404 | `NotFoundException` | «Запись не найдена.» |
| 409 | `ConflictException` | Текст сервера, например «На эту дату в зале уже есть активное бронирование» |
| 422 | `ValidationException` | «Ошибка валидации» + словарь `{поле: текст}` |
| 5xx | `ServerException` | «Ошибка на сервере. Попробуйте позже.» |
| таймаут | `NetworkException` | «Сервер не ответил вовремя.» |
| нет соединения | `NetworkException` | «Не удалось соединиться с сервером. Если сервер запущен, откройте консоль браузера и проверьте наличие ошибки CORS.» |
| отмена | `CancelledException` | Молча пропускается: запрос устарел |

### 4.3. Две особенности реализации

**Ошибки 4xx разбираются в интерсепторе, а не в `onError`.**
В `BaseOptions` задано `validateStatus: (status) => status < 500`, поэтому
коды 4xx попадают в `onResponse`, а не в ветку ошибок. Там они
превращаются в `DioException` с уже разобранным исключением в поле
`error`. Просто бросить `mapHttpError(...)` нельзя: dio перехватит любое
исключение из интерсептора и завернёт его в `DioException` с типом
`unknown`, а `ValidationException` окажется спрятан внутри поля `error`.

**Повторно разобранное исключение не разбирается второй раз.**
В `mapDioError` есть проверка `if (existing is ApiException) return existing`.
Без неё ошибка 422 пришла бы в приложение как `ServerException`, и
обработчик `on ValidationException` никогда не сработал бы.

### 4.4. Где происходит разбор

`lib/core/api_exceptions.dart`:

- `mapHttpError(status, body)` — по коду ответа и телу сообщения;
- `mapDioError(error)` — по типу `DioException`;
- `guard(action)` — обёртка, не выпускающая наружу `DioException`.

`lib/core/form_outcome.dart`:

- `toFormOutcome(error)` — превращает исключение в один из четырёх
  исходов формы: `FormSaved`, `FormInvalid`, `FormConflict`, `FormFailed`.

## 5. Ключи ошибок 422 совпадают с именами полей

Сервер отдаёт ошибки валидации в виде словаря, ключи которого совпадают
с именами полей модели:

```json
{
  "message": "Ошибка валидации",
  "errors": {
    "code": "Зал с таким кодом уже существует",
    "capacity": "Вместимость — положительное целое число"
  }
}
```

Поэтому ошибка ложится в нужное поле формы без ручного сопоставления:
форма хранит карту `_serverErrors` и подставляет её в `FieldSpec.serverError`.

## 7. Ошибка CORS: как проявилась, как обнаружена и что устранило

### 7.1. Как проявилась

Приложение загружено на `http://localhost:5555`, сервер отвечает на
`http://localhost:8080`. Это разные источники: различается порт.
Браузер не отдаёт странице ответ с другого источника, пока сервер
явно этого не разрешил.

В консоли браузера:

```
Access to XMLHttpRequest at 'http://localhost:8080/api/halls?sort=name%2Casc&page=1&size=10'
from origin 'http://localhost:5555' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

В коде Dart это выглядит неопознаваемо:

```
[API] сбой http://localhost:8080/api/halls?...: DioExceptionType.connectionError
```

`connectionError` в Dart неотличим от «сервер выключен». Поэтому в
текст `NetworkException` намеренно добавлена подсказка про CORS —
иначе на её поиск уходит несколько пар.

### 7.2. Как была обнаружена

По порядку из раздела 2.7 практической работы:

1. **Открыт ли сервер.** `http://localhost:8080/api/__health` отвечает —
   сервер запущен. Значит, дело не в нём.
2. **Консоль браузера (F12 → Console).** Сообщение со словом `CORS` —
   причина найдена.
3. **Вкладка Network.** Запрос `OPTIONS` виден, но сервер на него не
   отвечает разрешающими заголовками.
4. **Совпадает ли адрес.** `baseUrl` совпадает с адресом из
   `--dart-define`.

### 7.3. Что именно её устранило

Чинится только на сервере. Нижеизменения кода на стороне Flutter,
ни добавление заголовков в запрос через интерсептор, ни расширения
браузера не помогают — разрешение выдаёт сервер в ответе.

Сервер отдаёт на каждый ответ:

```
Access-Control-Allow-Origin: http://localhost:5555
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
```

и обрабатывает предварительный запрос `OPTIONS` на любом адресе,
отвечая `204` с теми же заголовками.

Предварительный запрос нужен потому, что `application/json` не входит в
список простых типов содержимого, а `POST` с телом JSON — это уже не
простой запрос. Поэтому без обработчика `OPTIONS` получается ровно то,
что описано в таблице типичных ошибок: `GET` работает, а `POST` — нет.

Отдельно: клиент запускается с фиксированным портом
(`--web-port=5555`). По умолчанию `flutter run -d chrome` каждый раз
выбирает случайный порт, источник меняется от запуска к запуску, и
сервер начинает отклонять запросы.

фотостудии, — но принципы те же. Ниже — что именно перенесено и как
проверено.

### 9.1. Шаг 07. Сервер вместо данных в памяти

| Принцип показательного проекта | Как в фотостудии |
|------------------------------|------------------|
| Реализация репозитория меняется, интерфейс остаётся | Интерфейсы `HallRepository`, `PhotographerRepository`, `ClientRepository`, `EquipmentRepository`, `BookingRepository` не изменились ни на строку. В `main.dart` подключены сетевые реализации |
| Экраны не переписываются | Экраны и формы не менялись с ПР3. Изменились только обработчики сохранения |
| Адрес сервера задаётся параметром сборки | `lib/core/config.dart`: `--dart-define=API_BASE_URL=...` |
| Таймауты настроены | `connectTimeout` 10 с, `receiveTimeout` 15 с |
| Перехватчик подставляет токен | `buildDio(tokenProvider: ...)` — токен подставляется в каждый запрос |

Отличие: показательный проект работает с PocketBase, здесь — с учебным
сервером, который повторяет его контракт. Это как раз оговорено в
методичке: «у вас — учебное API, но приём тот же».

### 9.2. Шаг 08. Загрузка, пустой список, ошибка

| Принцип показательного проекта | Как в фотостудии |
|------------------------------|------------------|
| Четыре состояния экрана: грузим, готово, пусто, сломалось | `LoadStatus` в `lib/state/list_notifier.dart` |
| Ошибки разбираются в одном месте, экраны не знают про Dio | `lib/core/api_exceptions.dart`: `mapDioError`, `mapHttpError`, `guard` |
| Отдельные виджеты состояний, в экране одна строка | `lib/widgets/state_views.dart`: `ListStateView`, `LoadingView`, `ErrorView`, `EmptyView`, `ForbiddenView` |
| Кнопка «Повторить» вызывает `refresh()` | `ErrorView(onRetry: notifier.load)` |
| Пустой список — третье состояние, а не пустой экран | `EmptyView` с сообщением и подсказкой |
| Перехватчик пишет по одной строке на запрос | `[API] → GET ...` и `[API] ← 200 ...` в `debugPrint` |
| Лог только в режиме отладки | Всё журналирование обёрнуто в `kDebugMode` |
| Кнопка обновления в шапке | `AppScaffold.onRefresh` — кнопка «Обновить данные» |
| Запросы независимы — уходят разом | `CatalogNotifier.load` использует `Future.wait` |

Текст ошибки про CORS добавлен намеренно: со стороны Dart ошибка CORS
неотличима от «сервер выключен», и без подсказки на её поиск уходят
часы.

### 9.3. Шаг 09. Вход и токен

| Принцип показательного проекта | Как в фотостудии |
|------------------------------|------------------|
| Токен живёт в отдельном хранилище | `SessionStore` в `lib/state/session.dart`, `SharedPreferences` |
| Роль в `localStorage` не лежит | Хранится только токен. Роль приезжает с сервера при восстановлении сессии |
| Сессия восстанавливается при запуске | `SessionStore.restoreUser` вызывает `GET /auth/me` |
| Протухший токен — молчаливый выход | `UnauthorizedException` → `clear()`, без сообщения об ошибке |
| Пока токен не проверен, решать рано | `AuthStatus.unknown` и `isKnown`: роутер не перенаправляет, пока идёт проверка |
| Роутер пересчитывает переходы при входе и выходе | `refreshListenable: session` в `createRouter` |
| Гость отправляется на экран входа с возвратом | `redirect` запоминает адрес в параметре `from` |

### 9.4. Шаг 10. Роли и права

| Принцип показательного проекта | Как в фотостудии |
|------------------------------|------------------|
| Все проверки прав в одном файле | `lib/core/permissions.dart` |
| Неизвестная роль трактуется как самая безобидная | `UserRole.parse` возвращает `UserRole.client` |
| Проверки на клиенте — удобство, а не защита | Правило на сервере проверяется отдельно (см. ниже) |
| Кнопки недоступных действий не показываются | `RecordActions.buttons`, `CreateButton`, `BulkActions` |
| Прямой адрес формы под чужой ролью → «Недостаточно прав» | `_GuardedForm` в `lib/core/router.dart`, экран `NoAccessScreen` |
| 403 превращается в понятное сообщение | `ForbiddenException` с текстом сервера |

**Главная проверка шага 10 — независимость от клиента.** Правила доступа
в учебном сервере открыты: приложение честно прячет от гостя все кнопки
изменения, но сервер всё равно проверяет права. Проверяется вручную:

```
DELETE /api/halls/1 без токена   → 401 «Требуется аутентификация»
DELETE /api/halls/1 роль client  → 403 «Операция доступна начиная с роли manager»
DELETE /api/halls/2 роль manager → 204
```

То есть гость, у которого в интерфейсе не было ни одной кнопки, всё
равно не может изменить данные: браузер просто отправил обычный
HTTP-запрос, а сервер его отклонил.

Это и есть настоящая защита: она работает независимо от того, что
происходит в браузере, и обойти её из клиента нельзя.

### 9.5. Отличия от показательного проекта

Отличия сознательные: они следуют из другой предметной области и из
того, что ПР3 в этом проекте уже сделан.

| Отличие | Причина |
|---------|---------|
| Папка `repositories/` вместо `data/` | Так называется слой в ПР2 этого проекта; менять имя слоя незачем |
| Папка `state/` вместо `providers/` | Тот же слой состояния, другое имя; `provider` используется и там, и тут |
| Свой сервер на Node.js вместо PocketBase | Учебный сервер из архива рассчитан на библиотеку, а тема — фотостудия |
| Свои роли: `client`, `photographer`, `manager`, `admin` | Домен фотостудии: администратор студии, менеджер смены, фотограф, клиент |
| Фильтрация, сортировка и страницы уходят на сервер | Показательный проект фильтрует на клиенте; в этой работе по заданию на оценку «5» фильтрация должна выполняться сервером |
| Есть отмена устаревших запросов и автоповтор | Требование ПР4 на оценку «5», в показательном проекте этого нет |
| Формы блокируют кнопку во время отправки | Требование ПР4 на оценку «5»: повторное нажатие не должно создавать вторую запись |

Всё, что касается архитектуры и порядка шагов, сделано так же, как в
показательном проекте: слои, репозитории, состояние, виджеты
состояний, правила прав и независимая проверка на сервере.

## 10. Что осталось от ПР3

Прежние реализации на данных в памяти (`in_memory_repository.dart`,
`in_memory_hall_repository.dart`, `in_memory_photographer_repository.dart`)
и прежние хранилища остались в проекте: на них написаны модульные тесты
из ПР3, и они показывают, что интерфейс репозитория не изменился.
В `main.dart` подключены сетевые реализации.

Хранилище `shared_preferences` по-прежнему используется только для токена
доступа. Пароль и признак администратора туда не кладутся: содержимое
`localStorage` пользователь видит в DevTools и может изменить. Проверка
прав всегда выполняется на сервере.
