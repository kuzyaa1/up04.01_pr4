# Практическая работа 4 Подключение REST API фотостудии

Проверка выполнена по документу «Практика 4 — подключение api».
Предметные аналоги примеров: книга → бронирование, ISBN → уникальный код
бронирования или зала, выдача без свободных экземпляров → занятый зал
или фотограф. Все рабочие коллекции относятся к фотостудии.

## Соответствие требованиям

| Требование | Реализация |
|---|---|
| Список из API через Dio | `main.dart`: пять `Api…Repository`; локальные хранилища не подключены |
| Адрес сборки, таймауты | `core/config.dart`, `core/api_client.dart`: `API_BASE_URL`, соединение 10 с, ответ 15 с |
| Загрузка, данные, пусто, ошибка и повтор | Все списки, `widgets/state_views.dart`; ошибки открытия форм также имеют повтор |
| Принудительная ошибка и задержка | API принимает `__fail` и `__delay`; параметры запуска клиента приведены ниже |
| Полный CRUD пяти сущностей | `ApiRepository`: чтение, создание, изменение, оба удаления, восстановление, массовые операции |
| Собственные исключения | `core/api_exceptions.dart`: `guard`, `mapDioError`, `mapHttpError`; виджеты не импортируют Dio |
| Журналирование | В debug выводятся метод, URL, статус; при сетевом сбое — отсутствие ответа и тип ошибки |
| 422 под полями | `FieldSpec.serverError`; исправление отклонённого значения снимает ошибку |
| 409 понятным сообщением | Конфликт даты/фотографа, удаление связанных записей, восстановление конфликтующей брони |
| Серверный поиск, фильтры, сортировка, страницы | Параметры каждого `Api…Repository`; `applyFilters`, `applySort`, `paginate` сервера |
| Отмена устаревшего поиска | Собственный `CancelToken` списка, защита состояния от устаревших ответов |
| Не более трёх попыток чтения | `withRetry`, интервалы 400 и 800 мс; изменения автоматически не повторяются |
| Кэш справочников | `CatalogNotifier`: 5 минут, общий выполняющийся запрос, все страницы; обновление после изменений |
| Защита повторного сохранения | `_saving`, отключённая кнопка и индикатор `EntityFormActions` |
| Не менее пяти тестов с подменённым Dio | `test/api_repository_test.dart`: параметры, страницы, 422, 409, недоступность, повтор и другие случаи |

Списки хранят текущую страницу. Полные коллекции загружаются отдельно для
кэшированных справочников и просмотра связей. Смена страницы списка
отправляет новый GET с новым `page`.

## Эндпоинты

Префикс: `http://localhost:8080/api`.
Коллекции: `halls`, `photographers`, `clients`, `equipment`, `bookings`.

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/:collection` | Страница, поиск, фильтры, сортировка |
| GET | `/:collection/:id` | Одна запись |
| POST | `/:collection` | Создание |
| PUT | `/:collection/:id` | Изменение |
| DELETE | `/:collection/:id` | Логическое удаление |
| DELETE | `/:collection/:id?hard=true` | Физическое удаление |
| POST | `/:collection/:id/restore` | Восстановление с проверкой ограничений |
| POST | `/:collection/bulk-delete` | `{ "ids": [1, 2] }`; логическое удаление |
| POST | `/:collection/bulk-delete?hard=true` | Физическое удаление; проверка набора до изменений |
| POST | `/bookings/:id/cancel` | Отмена активной брони |
| POST | `/bookings/:id/complete` | Завершение активной брони |
| POST | `/auth/login` | Вход, токен и профиль |
| GET | `/auth/me` | Профиль по токену |
| GET | `/__health` | Проверка доступности |

Чтение открыто для гостя. Изменение требует менеджера, физическое удаление
и восстановление — администратора. Сервер проверяет права независимо от UI.
Вошедший клиент получает свои бронирования.

## Преобразование ошибок

`HTTP / сетевая ошибка → интерсептор Dio → guard → ApiException → состояние списка / FormOutcome → виджет`.

401 → `UnauthorizedException`, 403 → `ForbiddenException`,
404 → `NotFoundException`, 409 → `ConflictException`,
422 → `ValidationException` с картой полей, 5xx → `ServerException`.
Отсутствие сети и таймаут → `NetworkException`; отмена → `CancelledException`
без сообщения и без повторных запросов.

API использует `fullName` для имени клиента, форма ПР3 — `name`;
ошибка явно передаётся в поле имени. ФИО фотографа собирается из фамилии
и имени. Бронь читает вложенные `hall` и `client`, на запись отправляет ID.

## CORS и воспроизведение состояний

Разные порты 5555 и 8080 означают разные источники. Сервер возвращает
`Access-Control-Allow-Origin: http://localhost:5555`, разрешает методы
и заголовки `Content-Type, Authorization`, обрабатывает `OPTIONS` ответом 204.
Проверены автоматический preflight и получение списка в браузере.

Фактически воспроизведённый случай: сервер запущен с
`--origin http://localhost:5556`, клиент оставлен на 5555. В браузере список
сменился сетевой ошибкой, хотя сервер получал GET и возвращал 200.
Проверка `/__health` отдельно также дала 200, но заголовок
`Access-Control-Allow-Origin` содержал `http://localhost:5556` вместо 5555.
Так установлена причина: несовпадение источников, а не выключенный сервер.
После перезапуска с `--origin http://localhost:5555` и повтора запроса
список снова загрузился. Снимок сбоя — `screenshots/05-cors-error.jpg`.
Для самостоятельной диагностики дополнительно проверяют Console и Network;
в данном прогоне источник проблемы подтверждён заголовком ответа и
контрольной сменой единственного параметра `--origin`.

Другой сервер:

```powershell
flutter run -d chrome --web-port=5555 --dart-define=API_BASE_URL=http://192.168.1.10:8080/api
```

Индикатор через настоящий `__delay=1500` в GET списка:

```powershell
flutter run -d chrome --web-port=5555 --dart-define=API_DEMO_DELAY_MS=1500
```

Принудительный `__fail=500`:

```powershell
flutter run -d chrome --web-port=5555 --dart-define=API_DEMO_FAIL=500
```

После демонстрации запустить без этих параметров. Для недоступности
остановить сервер API и нажать «Обновить данные»; после возврата сервера —
«Повторить». Для пустого результата искать отсутствующий зал.

422: изменить код зала на код другого зала. 409: создать бронь с другим
кодом на уже занятый зал и день. Выбрать дату не в прошлом и совместимого
с залом фотографа. Модель ПР3 выбирает день без времени: активная бронь
занимает зал и фотографа на день; длительность используется в стоимости.

## Отказ удаления связанных записей

Удаление зала, клиента или фотографа теперь проверяется сервером без
предварительного блокирования в экране. После подтверждения отправляется
DELETE, а для массовой операции — POST bulk-delete. Если остались зависимости,
API возвращает 409 с их количеством. Приложение показывает окно
«Операция не выполнена» с причиной отказа и кнопкой «Понятно».
Список, данные и выделение сохраняются. Физическое удаление также учитывает
связи из корзины, чтобы восстановление не создавало потерянные ссылки.

Это ожидаемый отказ операции, а не падение приложения. Чтобы удалить такую
запись, сначала перенесите или удалите связанные записи. Сервер не удаляет
их каскадно. Для просмотра 409 в Network можно подтвердить удаление
используемого зала; полный текст причины находится в Response.

`test/deletion_conflict_test.dart` проверяет сетевой 409, отображение окна,
закрытие окна, сохранение списка и выделения для обоих видов одиночного
и массового удаления с подменённым HTTP-адаптером.
